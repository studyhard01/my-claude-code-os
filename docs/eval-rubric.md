# push 게이트 평가 rubric (M1)

> **push 전에 서비스가 "실제로 동작하는가"를 기계적으로 판정하는 기준.**
> 실행 = `npm run eval` (구현: `scripts/evaluate.ts`). **전 항목 통과(100점)일 때만 push 한다.**
> 절차는 `/ship` 스킬이 담당: 평가 통과 → push, 실패 → push 중단 + 원인 보고.
>
> 왜 전 항목 통과인가: M1 은 기능 수가 적어(API 8종) 부분 점수로 봐줄 "덜 중요한 기능"이
> 없다. 항목이 늘어나 가중치 판단이 필요해지면 그때 기준선을 낮춘다.

## 평가 항목

| # | 항목 | 통과 기준 | 배점 |
|---|------|-----------|------|
| A1 | 타입 검사 | `npm run typecheck` 종료코드 0 | 15 |
| A2 | 단위 테스트 | `npm test` (vitest) 전부 통과 | 15 |
| B1 | 서비스 기동 | dev 서버가 90초 안에 뜨고 HTTP 응답 | 10 |
| C1 | 피드 목록 | `GET /api/jobs` → 200, 계약 형태(items·totalCount·partialHiddenCount·nextCursor) | 8 |
| C2 | 정렬 | `?sort=recent` → 200, postedAt 내림차순 | 5 |
| C3 | 필터 | 목록에 실존하는 role 로 `?role=` → 200, **1건 이상** + 전부 jobRole 일치 (0건이면 빈 배열 탓에 항상 참이 되므로 실존 role 사용) | 5 |
| C4 | 상세 + 에러 계약 | 실존 id → 200·id 일치 / 없는 id → 404·`{error:{code,message}}` | 7 |
| C5 | 북마크 왕복 | POST → 목록 확인 → PATCH(APPLIED) → DELETE → 목록에서 소멸 | 10 |
| C6 | 사용자 조건 | GET → 200·roles 배열, 같은 값 PUT → 200 (비파괴 왕복) | 5 |
| D1 | 응답 시간 — 목록 | `GET /api/jobs` 워밍업 후 5회: 평균 < 500ms, 최대 < 1500ms | 12 |
| D2 | 응답 시간 — 상세 | `GET /api/jobs/:id` 5회: 평균 < 500ms | 8 |

**합계 100점. 게이트 = 100점 (하나라도 실패하면 push 금지).**

## 설계 근거

- **A(정적 검증)**: 계약 위반을 잡는 유일한 기계 수단이 typecheck 이므로 필수 (CLAUDE.md).
- **C(기능)**: M1 완료 기준인 "온보딩(C6)→피드(C1~C3)→상세(C4)→북마크(C5)" 흐름을
  API 계약(`contract.ts`·OS.md 12.5) 그대로 검증한다. C5 는 만들고 지우므로 반복 실행해도 안전.
- **D(응답 시간)**: dev 모드 + SQLite 로컬 기준의 느슨한 상한. 목적은 성능 튜닝이 아니라
  "N+1 쿼리·무한 대기 같은 회귀를 push 전에 감지"하는 것. 첫 요청은 컴파일 비용이 섞이므로
  워밍업 후 측정한다.
- **평가 서버는 3100 포트**를 쓴다 — 사용자가 3000 에서 띄워 둔 dev 서버와 충돌하지 않게.
