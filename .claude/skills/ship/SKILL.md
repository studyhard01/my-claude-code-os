# Ship — 평가 통과 시에만 push

**push 는 사람이 아니라 평가가 허가한다.** 2026-07-14 사용자 결정: 루프 이후의 push 는
완전 허용하되, **push 전에 서비스 평가(rubric = `docs/eval-rubric.md`)를 통과해야 한다.**
이 스킬이 그 게이트다. (병목 ① "사람이 유일한 직렬 구간"의 push 부분 해소)

## 절차

1. **커밋 확인** — `git status` 로 작업 트리가 깨끗한지 확인한다.
   - 커밋 안 된 변경이 있으면 먼저 `/commit` 절차로 커밋한다(그 안에 typecheck·test 게이트 포함).
   - push 할 새 커밋이 없으면(로컬 = origin) 그대로 알리고 종료한다.

2. **평가 실행** — `npm run eval` (2~3분 소요, 3100 포트에 평가 서버를 따로 띄운다).
   - rubric 11항목: 정적 검증(A) + 기동(B) + 기능 8종 API 왕복(C) + 응답 시간(D).
   - **전 항목 통과(100/100)일 때만 다음 단계로.**

3. **판정에 따라**:
   - **PASS** → `git push origin HEAD` (force 금지 — 역사를 다시 쓴 경우는 이 스킬 범위 밖,
     사용자에게 알리고 멈춘다). push 후 원격 CI 가 한 번 더 검증한다.
   - **FAIL** → push 하지 않는다. 실패 항목·측정값을 사용자에게 보고하고,
     원인이 명백하면 고친 뒤 **커밋부터 다시**(1번으로). 불명확하면 사용자에게 묻는다.

4. **마무리** — push 결과(커밋 범위)를 한 줄로 보고한다. STATUS.md 갱신이 필요한
   작업 단위였다면 갱신을 잊지 않는다.

## 주의

- 평가를 건너뛰는 예외는 없다. 문서-only 변경도 게이트를 통과시킨다(빨리 끝난다) —
  "이건 괜찮겠지"가 낭비 ②(무게이트 커밋)를 만들었던 전례가 있다.
- 3100 포트가 이미 사용 중이면 스크립트가 실제 포트를 로그에서 읽어 따라간다.
- 평가 서버가 90초 안에 안 뜨면 B1 실패로 전체 FAIL — dev.db·node_modules 존재를 먼저 의심할 것(CLAUDE.md 실행 명령 참조).
